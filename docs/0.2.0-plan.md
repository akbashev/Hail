# Hail 0.2.0 plan

Status: proposal

Hail 0.1 establishes a durable logical agent: a stable virtual-actor identity, an event-sourced semantic state reducer, explicit effect authorities, and replaceable model endpoints. The 0.2.0 release should make the failure semantics equally explicit.

The central goal is to close the gap between **durable semantic state** and **durable execution**.

An agent should be able to answer, after a process or node failure:

- Was this caller command accepted?
- Which model decision was committed?
- Which external effects may have happened?
- Was this inter-agent message accepted by its recipient?
- What authority did the original command have?

## Design position

Semantic history and execution progress are separate domain concerns, but they do not need separate physical stores in 0.2.0. Start with one append-only journal containing typed semantic and execution events. Project and retain those categories differently later, once the transaction and recovery semantics are proven.

The durable journal remains the source of truth for the agent's meaning. The execution records explain how an incomplete command is resumed without asking nondeterministic systems to recreate decisions that were already committed.

The implementation should remain functional at the domain boundary:

- commands, events, decisions, and effect requests are immutable values;
- state reconstruction is a pure reducer;
- orchestration is an explicit process manager around that reducer;
- the host interprets effects and supplies policy;
- recovery is a state transition, not an ad-hoc retry loop.

## 0.2.0 guarantees

| ID | Guarantee | Meaning |
| --- | --- | --- |
| G1 | Stable identity | A known AgentID is addressable regardless of node, activation, or passivation. |
| G2 | Deduplicated commands | Reusing a CommandID does not execute the logical command twice. |
| G3 | Reliable messages | An accepted inter-agent message is not lost; duplicate delivery is one logical message. |
| G4 | Non-widening recovery | Recovery may preserve or reduce authority, never increase it. |
| G5 | Deterministic state replay | Folding the same semantic journal produces the same AgentState. |
| G6 | Durable decisions | A committed model decision is not regenerated after a crash. |
| G7 | Explicit effect semantics | Hail reports retryable, completed, and uncertain effects honestly; it only offers exactly-once behavior when the effect protocol can establish it. |
| G8 | Lifecycle transparency | Passivation changes resource use, not logical existence. |

These are runtime guarantees, not prompt instructions. Tests and documentation must be written against them.

## Target domain model

### Command admission

Add a caller-visible, typed command identity and persist acceptance atomically with the turn opening:

~~~swift
struct CommandID: RawRepresentable, Codable, Hashable, Sendable {
    let rawValue: UUID
}

struct AgentCommand<Input: Codable & Sendable>: Codable, Sendable {
    let id: CommandID
    let input: Input
    let authority: AuthorityGrantRef
    let correlationID: CorrelationID?
    let causationID: CausationID?
}
~~~

The exact generic envelope may change, but the boundary must carry these semantics. A command is not accepted until its durable commandAccepted event is committed. This replaces the current recoverability gap between turnStarted, turnIdentified, and messageReceived.

Existing events remain readable for journal compatibility. New code writes the atomic admission event; the reducer keeps a legacy path for older journals.

### Authority references

An arbitrary closure-based Authority cannot be reconstructed safely after activation. Resumable commands therefore persist a host-resolvable reference rather than a closure:

~~~swift
struct AuthorityGrantRef: Codable, Hashable, Sendable {
    let profile: AuthorityProfileID
    let revision: UInt64
}
~~~

The host resolves the current policy and intersects it with the original grant. If the authority cannot be named and reconstructed, the command is not automatically resumable; it fails closed and requires host reconciliation.

### Durable execution steps

The minimum execution vocabulary is:

~~~text
commandAccepted
modelRequestStarted
modelDecisionCommitted
effectRequested
effectCompleted | effectUncertain
responseCommitted
commandCompleted | commandFailed
~~~

modelDecisionCommitted contains the normalized assistant text, tool calls, and final output needed to continue. A crash after this event resumes from the committed decision; it does not issue another LLM request.

Every outside-world operation receives an EffectInvocationID and declares a reliability class:

~~~swift
enum EffectReliability: Codable, Sendable {
    case readOnly
    case idempotent
    case reconcilable
    case compensatable
    case atLeastOnce
}
~~~

If an effect was requested but its completion is absent after recovery, the runtime applies that class. An unknown external outcome becomes effectUncertain, never an implicit duplicate retry.

### Durable agent messaging

AgentTool.send should enqueue a durable message and return a queue/acceptance result, not claim delivery after spawning an in-memory Task.

~~~text
outboundEnqueued(messageID, recipient, payload)
       -> recipient inboundAccepted(messageID)
       -> sender outboundAcknowledged(messageID)
~~~

The recipient deduplicates MessageID. Delivery retries are safe because acceptance is idempotent.

### Logical catalog versus activation directory

Maintain two projections:

- **Agent catalog:** durable knowledge that an AgentID exists and how it may be activated.
- **Activation directory:** ephemeral knowledge that an agent is currently resident.

AgentTool checks the catalog before asking getActor. Passivation removes only the activation entry, so a known inactive agent can be reactivated without permitting hallucinated IDs to create new entities.

### Reproducible model context

Add revisions or hashes to model request descriptors:

- definition revision;
- tool-set/schema revision;
- prompt-assembler revision;
- context-manifest hash;
- protocol/runtime revision.

These identify the inputs used by a warm provider session. They improve auditability without persisting secrets or claiming that current external context is deterministic.

## Delivery phases

### Phase 0 — contracts and compatibility

- Add typed IDs: CommandID, MessageID, EffectInvocationID, CausationID, and CorrelationID.
- Add versioned authority references and host resolution APIs.
- Define new event cases and legacy decoding/reduction behavior.
- Document which existing APIs provide no deduplication when they generate an ID internally.

Exit criterion: old journals replay; new event fixtures encode/decode across a version boundary.

### Phase 1 — safe admission and recovery

- Replace the three-event turn admission sequence with atomic commandAccepted.
- Persist the command's authority reference and resume policy.
- Remove the recovery path that calls stream(message) without the original authority.
- Mark commands with non-reconstructable authorities as non-resumable.
- Return the previously committed result for a repeated CommandID.

Exit criterion: a crash at every admission boundary loses no accepted command and cannot widen authority.

### Phase 2 — durable decisions and effects

- Commit normalized model decisions before executing their tool calls.
- Add effect invocation state and idempotency keys.
- Resume from the last committed execution step.
- Represent unresolved external outcomes as uncertain and expose reconciliation to the host.
- Keep provider sessions as caches; the journal remains authoritative.

Exit criterion: a crash after a model result never causes a second model decision, and an effect is retried only according to its declared reliability.

### Phase 3 — messaging and lifecycle transparency

- Implement durable outbox/inbox delivery with MessageID deduplication.
- Change agent-tool wording from “Delivered” to “Queued” until recipient acceptance is durable.
- Keep the active-agent directory as a rebuildable liveness projection, never as
  the source of existence or routing truth.
- Route by stable agent IDs so passivation and process restart reactivate the
  journal-backed virtual actor. If a product needs admission/rejection of
  unknown IDs, make that an explicit policy backed by durable agent state.

Exit criterion: random crashes and duplicate deliveries produce one logical inter-agent message, and passivation does not change existence.

### Phase 4 — audit, projections, and hardening

- Add model input descriptors and configuration fingerprints.
- Expose execution history as a projection separate from conversation history.
- Treat compaction as context management; build episodic/task/fact memory as rebuildable projections.
- Add deterministic failpoints and property-based crash tests.
- Publish the guarantees and recovery matrix in the API documentation.

Exit criterion: replay, audit, and projection tests pass from the same journal after arbitrary injected failures.

## Failure-injection matrix

The test harness should be able to fail after each boundary:

~~~text
before/after commandAccepted
before model invocation
after provider result
after modelDecisionCommitted
before/after effect execution
after external effect, before effectCompleted
before/after responseCommitted
before receiver acceptance
after receiver acceptance, before sender acknowledgement
~~~

For generated crash schedules, assert:

- accepted commands are never lost or logically duplicated;
- restricted commands never gain capabilities;
- committed model decisions are never regenerated;
- idempotent effects are not duplicated;
- uncertain effects are surfaced;
- accepted messages are eventually delivered once;
- state replay remains deterministic.

## Package responsibilities

- **HailCore:** domain IDs, command/event values, authority references, pure reducers, and effect reliability contracts.
- **HailAgentRuntime:** command admission, recovery process management, execution-step orchestration, and outbox/inbox coordination.
- **HailModelRuntime:** provider invocation and normalized decision boundaries; no hidden retry or product policy.
- **HailCompaction:** context projections and journaled summaries, not canonical agent memory.
- **Host application:** authority profiles, workspace resolution, durable catalog policy, effect interpreters, and reconciliation of uncertain effects.

## Non-goals for 0.2.0

- Generic exactly-once guarantees for arbitrary external HTTP or shell operations.
- Static information-flow security claims for Classified or ScopedEffect.
- Replacing Swift distributed actors with a workflow engine.
- Making A2A or MCP internal domain primitives; they should remain adapters.
- Making vector retrieval the canonical memory store.
- Adding provider-specific defaults or orchestration patterns to Hail core.

## Release bar

Hail 0.2.0 is ready when G1–G8 are either implemented and tested or explicitly removed from the public guarantee set. The release should prefer a smaller, honest API over automatic recovery that can duplicate effects, lose messages, or widen authority.
